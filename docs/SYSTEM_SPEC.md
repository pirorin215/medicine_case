## 1. システムアーキテクチャ

### 1.1 全体構成

このシステムは、マイコン側（ファームウェア）とスマートフォンアプリ側（Android）が連携して動作します。

```
┌─────────────────┐         ┌─────────────────┐
│   マイコン       │         │  スマートフォン   │
│   (Firmware)     │         │  (Android App)   │
└─────────────────┘         └─────────────────┘
        │                              │
        │ 1. BLE接続                    │
        │──────────────────────────────>│
        │                              │
        │ 2. 時刻同期                     │
        │ <─────────────────────────────│
        │ SET:time:1779600124           │
        │                              │
        │ 3. 応答                        │
        │──────────────────────────────>│
        │ OK:time                       │
        │                              │
        │ 4. 服薬検出                    │
        │                              │
        │ 5. INTAKE通知                  │
        │──────────────────────────────>│
        │ INTAKE:1716546645             │
        │                              │
        │ 6. 重複チェック（スマホ側）      │
        │    - 既に処理済みなら無視       │
        │    - 新しいイベントなら記録     │
```

### 1.2 責任分割

```
ファームウェア（シンプル）         スマートフォンアプリ（管理担当）
─────────────────────         ─────────────────────
服薬を検出                      スケジュール管理
  ↓                              ↓
timestampを1つだけ保持           ①服薬データを取得
  ↓                              ↓
INTAKE:timestamp をBLE通知       ②時刻補完（timestamp=0なら受信時刻使用）
（マイコン側はデータを保持したまま）↓
                                ③重複チェック（既に処理済みなら無視）
                                  ↓
                                ④通知判定・履歴表示
```

**設計原則**:
- マイコン側は「服薬検出」のみに専念
- スケジュール管理・通知・履歴はすべてスマートフォンアプリ側で実行
- 時刻同期は推奨ですが、必須ではありません
- **データ消失防止**: スマホ側で重複排除を実装し、マイコン側のデータは保持したままにする

## 2. 服薬検出仕様（マイコン側）

### 2.1 検出原理

薬ケースの傾きを6軸センサー（LSM6DS3TRC）で検知し、その角度変化を「服薬動作」として判定します。

### 2.2 ハードウェア構成

| 項目 | 仕様 |
|:---|:---|
| **センサー** | LSM6DS3TRC (6軸IMU) |
| **加速度計** | 3軸 (X, Y, Z) |
| **ジャイロスコープ** | 3軸 (roll, pitch, yaw) |
| **サンプリングレート** | 100ms間隔 |
| **測定範囲** | ±90度（pitch, roll） |

### 2.3 状態遷移

```
IDLE（待機）→ MOVING（移動中）→ CONFIRMED（確定）→ IDLE
```

#### 各状態の詳細

**IDLE状態**
- クールダウン期間中は移動検出をスキップ
- 初期位置をセット（現在のpitch, rollを記録）
- 変化量を監視（pitch, rollの変化を計算）
- 変化量 = sqrt(pitchChange² + rollChange²)
- 閾値超過でMOVING状態へ遷移

**MOVING状態**
- 安定待ち時間（500ms）を経過するのを待つ
- または強制終了時間（2000ms）で強制的に遷移
- 最大変化量を記録（各時点での最大値を保持）

**CONFIRMED状態**
- 最大変化量が閾値を超えているか確認
- 超えていればINTAKEとして記録
- IDLE状態に戻る

### 2.4 判定基準

#### 角度閾値

| 項目 | 仕様 |
|:---|:---|
| **デフォルト** | 70.0度 |
| **設定範囲** | 10.0度 ～ 180.0度 |
| **単位** | 度（degree） |

#### クールダウン時間

| 項目 | 仕様 |
|:---|:---|
| **デフォルト** | 30000ms (30秒) |
| **設定範囲** | 1000ms ～ 300000ms |
| **目的** | 連続検出防止 |

#### 固定パラメータ

| パラメータ | 値 | 説明 |
|----------|-----|------|
| センサー更新間隔 | 100ms | 定期的に角度を計算 |
| 安定待ち時間 | 500ms | 安定確認用 |
| 強制終了時間 | 2000ms | 安定待ちの最大時間 |
| 移動平均係数 | 0.8 | 平滑化用（alpha値） |

### 2.5 INTAKE記録

#### 記録条件

1. 最大変化量が閾値を超えている
2. 安定待ち時間が経過している

#### タイムスタンプ

- **時刻同期済み**: 現在のUnixタイムスタンプを記録
- **時刻未同期**: 0を記録（スマホ側で受信時刻を使用して補完）

### 2.6 LEDフィードバック

#### INTAKE検出時

- **パターン**: 緑色点滅（300ms ON / 200ms OFF）
- **回数**: 6回（計3秒間）
- **目的**: ユーザーへの視覚的フィードバック

#### 通常時

- **色**: 接続状態・時刻同期状態で変化
- **点灯**: 常時点灯

### 2.7 通信

#### INTAKE通知

- **トリガー**: INTAKE検出時
- **フォーマット**: `INTAKE:<unix_timestamp>` または `INTAKE:0`
- **宛先**: Sensor characteristic
- **即時送信**: 検出直後に送信

### 2.8 エラーハンドリング

| エラー種別 | 対応 |
|----------|------|
| **LSM6DS3検出失敗** | 起動時のみリトライ、実行時はスキップ |
| **値異常** | ログ出力して処理継続 |
| **NaN値** | ログ出力して処理継続 |
| **オーバーフロー** | ログ出力して処理継続 |

## 3. 通知・履歴管理仕様（アプリ側）

### 3.1 服薬スケジュール設定

アプリでは「朝」「昼」「夜」の3つの時間枠を管理します。

| 項目 | デフォルト範囲 | 説明 |
|:---|:---|:---|
| **朝 (MORNING)** | 08:00 - 11:00 | スケジュールID: 0 |
| **昼 (AFTERNOON)** | 12:00 - 17:00 | スケジュールID: 1 |
| **夜 (EVENING)** | 19:00 - 22:00 | スケジュールID: 2 |

- ユーザーは各枠の有効/無効、開始・終了時刻、および**通知推奨時刻（スロット内通知用）**を自由に設定可能です
- 通知には「スロット内（攻め）の通知」と「スロット終了後（守り）の通知」の2種類があります

### 3.2 通知ロジック

#### チェック間隔

| 状況 | チェック間隔 |
|:---|:---|
| **バックグラウンドサービス** | 10秒ごと（BLEスキャンまたは接続中） |
| **WorkManager** | 最速15分ごと（アプリ停止時やDozeモード時） |
| **リマインダー間隔** | ユーザー設定（デフォルト60分） |

#### 通知のトリガー条件（スロット終了後 / 追い通知）

未服薬の枠があり、かつ現在時刻がその枠の終了時刻を過ぎている場合、以下のルールで通知します。

| 接続状態 | 挙動 | 理由 |
|:---|:---|:---|
| **BLE未接続** | **1回のみ通知** | 外出中などケースが手元にない場合に、リマインダーが鳴り続けるのを防ぐため |
| **BLE接続中** | **リマインダー継続** | ケースが近くにあるのに服用していないため、設定間隔ごとに通知を継続 |
| **接続確立時** | **即時通知** | 接続した瞬間に未服薬の枠があれば、前回の通知からの経過時間に関わらず即座に通知（強制通知） |

- **初回通知優先ルール**: スロット終了後の最初の1回目の通知は、インターバル制限を無視して即座に送信されます

#### インテリジェント・リマインダー（スロット枠内通知）

スロットの終了時刻を待たずに、枠内で最適なタイミングで一度だけ通知を送る仕組みです。

**トリガー条件**:
1. 現在時刻が設定された**「通知推奨時刻」**に到達した
2. スロット時間枠内に帰宅し、**BLE接続が確立**された（チャンス通知）

**制約**: スロット内での通知は、その枠につき**1日最大1回**に限定されます（推奨時刻かBLE接続のどちらか早い方）

#### 通知判定の対象（直近枠ルール）

通知の対象となるのは、**「現在時刻において、すでに終了時刻を過ぎている有効な枠」のうち、最も遅い（最新の）時間帯の1枠のみ**です
※枠内通知（インテリジェント・リマインダー）はこのルールの外で、現在進行中の枠に対して行われます

### 3.3 服薬記録 (INTAKE) ロジック

#### 記録の分類と3状態管理

受信した時刻に基づき、どの枠の服薬として保存するかを自動判定します。

1. **枠内での服薬**: 現在時刻がいずれかの有効なスケジュール範囲内であれば、その枠の記録として保存
2. **通知後の服薬**: 枠外であっても、直近の通知から一定時間内（リマインダー間隔の2倍）であれば、直前の枠の服薬として記録
3. **有効フラグの保存**: 記録作成時にその時のスケジュール設定（有効/無効）を保存し、履歴画面で「対象外（ー）」を表示可能にします

#### 服薬検知時刻とスマホ受信時刻の別保存

スタンドアロン動作（BLE未接続時の服薬検知）を正確に記録するため、服薬検知時刻とスマホ受信時刻を別々に保存します。

- **服薬検知時刻**: マイコンが服薬を検知した時刻
- **スマホ受信時刻**: スマホがINTAKEイベントを受信した時刻

これにより、BLE未接続時の服薬検知でも、実際の服薬タイミングを正確に記録できます。

#### スケジュール変更時のリセット

- 設定変更時、整合性を保つため**当日分の服薬記録は自動的に未服用状態へリセット**されます

#### 当日レコードの自動生成

- アプリ起動時、または日付変更後の最初のチェック時に、**その日の未服用レコードを自動的に作成**します

## 4. データ同期とスタンドアロン動作

### 4.1 スタンドアロン動作の概要

マイコンはBLE未接続時でも服薬を検知・記録できるため、スマートフォンアプリは再接続時にスタンドアロン中の服薬データを自動取得します。

### 4.2 処理フロー

1. BLE接続確立時、アプリは自動的に`GET:intake`コマンドを送信
2. マイコンは保存されている最新のINTAKEタイムスタンプを返す
3. アプリは受信したタイムスタンプを「服薬検知時刻」として記録
4. 同時に、イベントを受信した時刻を「スマホ受信時刻」として記録
5. **重複チェック**: 既に処理したタイムスタンプであれば、記録をスキップ

これにより、外出先などでBLE未接続の状態で服薬をした場合でも、帰宅後にBLE接続すれば正確に記録できます。また、通信エラー等によるデータ消失を防ぐため、マイコン側のデータは保持されたままになります。

### 4.3 BLE接続時の自動シーケンス

BLE接続時に以下のコマンドを自動送信します：

1. 時刻同期（`SET:time`）
2. ファームウェアバージョン取得（`GET:version`）
3. スタンドアロン中の服薬データ取得（`GET:intake`）

**注記**: マイコン側のデータはクリアしません。重複排除はスマホ側で実装します。

BLE OFF→ONの再接続時にも確実にデータを取得するため、接続時にサービス準備状態をリセットする設計になっています。

### 4.4 2時刻管理のメリット

| 状況 | 服薬検知時刻 | スマホ受信時刻 | 活用方法 |
|:---|:---|:---|:---|
| **BLE接続中** | 実際の服薬時刻 | ほぼ同じ | 正確な記録 |
| **BLE未接続** | 0（不明） | 接続時の時刻 | 補完として使用 |
| **時刻未同期** | 0（不明） | 受信時刻 | 補完として使用 |

スマホアプリは、`服薬検知時刻`が0の場合、`スマホ受信時刻`を代わりに使用して記録します。

## 付録：検証済みの主要ユースケース

### ユースケース A: BLE未接続での終了時刻到達
1. 夜の枠が22:00に終了。BLEは切断状態
2. 22:00過ぎに「夜の服薬がまだです」と通知が1回届く
3. その後も未接続なら、リマインダー通知は来ない

### ユースケース B: 通知後のBLE接続（強制通知）
1. ユースケースAの状態
2. 薬ケースに近づき、BLEが接続される
3. **即座に**「夜の服薬がまだです」と強制通知が届く

### ユースケース C: BLE接続中でのリマインダー
1. ユースケースBの後、服用せずに放置
2. 設定したリマインダー間隔（例：1分）ごとに通知が届く
3. 服用すると通知が止まる

### ユースケース D: スロット枠内での推奨時刻通知
1. 昼の枠（10:00-21:00）で、通知推奨時刻を12:00に設定
2. 12:00になり、未服薬であれば「服薬の時間です」と通知が届く
3. その後は21:00（終了時刻）まで、未服薬であってもリマインダーは届かない

### ユースケース E: スロット枠内でのチャンス通知（BLE接続）
1. 昼の枠（10:00-21:00）で、まだ12:00（推奨時刻）前
2. 11:30に帰宅し、BLEが接続される
3. **即座に**「服薬の時間です」と通知が届く（チャンス通知）
4. この時点で「枠内通知済み」となるため、12:00の通知は行われない
