# データフロー仕様書

## 概要

このドキュメントは、Medicine Caseシステムにおけるマイコンとスマートフォンアプリ間のデータフローと状態管理の仕様を詳細に説明します。

## 基本設計思想

**「スマホとマイコンは常時接続されていない」**ことを前提として設計されています。

- マイコン側は極力シンプルにする
- 複雑な状態管理はスマホ側で行う
- 接続されていない間のイベントは、マイコン側で最小限の情報だけ保持する

## 1. マイコン側の状態管理

### 1.1 保持する状態

マイコン側は**1つの値のみ**を保持します：

```cpp
uint32_t g_lastIntakeTimestamp;  // 0 = 未取得（服薬していない状態）
                                 // >0 = 最後の服薬検出時のUnixタイムスタンプ
```

### 1.2 状態遷移

```
初期状態
  ↓ 服薬検出
服薬済み状態 (g_lastIntakeTimestamp = 1748762345)
  ↓ スマホから CLR:intake 受信
初期状態 (g_lastIntakeTimestamp = 0)
```

**重要**: マイコンは「いつ服薬したか（timestamp）」のみを保持し、「何回服薬したか」はカウントしません。

### 1.3 服薬検出時の処理

```cpp
void detectMedicineIntake() {
    // 1. 角度変化を検出
    if (movementAngle >= threshold) {
        // 2. 現在時刻を記録
        g_lastIntakeTimestamp = g_currentTimestamp;

        // 3. LEDフィードバック（緑点滅3秒）
        blinkGreenLED();

        // 4. BLE通知を送信試行（接続されていなければ送信されない）
        sendSensorNotification("INTAKE:%u", g_lastIntakeTimestamp);

        // 5. クールダウン開始（連続検出防止）
        startCooldown();
    }
}
```

**ポイント**:
- 通知の送信成功/失敗に関わらず、timestampは保持される
- スマホが接続されていなくても、時刻は記録される

## 2. スマホ側のデータ取得戦略

### 2.1 アクティブポーリング（能動的取得）

スマホ側が明示的に取得しに行くタイミング：

1. **BLE接続確立時**
   - 接続完了後、即座に `GET:intake` を送信
   - 見逃していた服薬イベントを取得

2. **スケジュール時刻到来時**（将来実装予定）
   - 設定した時刻（朝7:00、昼12:00、夜19:00）になったらポーリング
   - その時間に服薬したかを確認

### 2.2 パッシブ受信（受動的受信）

マイコンからの通知を受け取る：

- `INTAKE:<timestamp>` 通知を受信したら即座に処理
- 接続されている間のみ受信可能

### 2.3 取得〜クリアのフロー

```
1. スマホ: GET:intake 送信
2. マイコン: INTAKE:1748762345 応答（または NONE）
3. スマホ:
   - INTAKE受信時:
     a. ローカルDBに服薬記録を保存
     b. マイコンに CLR:intake 送信
   - NONE受信時:
     - 何もしない
4. マイコン: g_lastIntakeTimestamp = 0 にクリア
```

## 3. BLE通信プロトコル詳細

### 3.1 服薬取得コマンド

**リクエスト**（スマホ → マイコン）:
```
GET:intake
```

**レスポンス**（マイコン → スマホ）:
```
INTAKE:<timestamp>   # 未取得の服薬がある場合（timestampはUnix秒）
NONE                  # 未取得の服薬がない場合
```

**使用例**:
```bash
# 服薬記録がある場合
GET:intake
→ INTAKE:1748762345

# 服薬記録がない場合
GET:intake
→ NONE
```

### 3.2 服薬クリアコマンド

**リクエスト**（スマホ → マイコン）:
```
CLR:intake
```

**レスポンス**（マイコン → スマホ）:
```
OK: Intake cleared
```

**使用例**:
```bash
CLR:intake
→ OK: Intake cleared
```

## 5. 仕様の妥当性評価

### 5.1 現状仕様の評価

**✅ 良い点**:
- マイコン側は1つの変数のみを保持（シンプル）
- 接続されていない間も時刻を記録可能
- ポーリングで見逃しを回収可能

**⚠️ 注意点**:
- スマホが長期間接続しない場合、次の服薬で上書きされる
  - 例: 朝7:00に服薬 → timestamp記録 → スマホ未接続
  - 昼12:30に服薬 → timestamp上書き（朝の記録消失）

### 5.2 上書き問題への対策案

**案1: 複数タイムスタンプ保持**
```cpp
// マイコン側で直近N回分を保持（例: 3回分）
uint32_t g_intakeTimestamps[3];
uint8_t g_intakeCount;
```
- メリット: 短期間の見逃しに対応
- デメリット: マイコン側の複雑化、メモリ消費

**案2: RTCバックアップ**
```cpp
// RTCレジスタにtimestampを保存（電源切断でも保持）
RTC.setBackupRegister(g_lastIntakeTimestamp);
```
- メリット: 電源切断でも記録保持
- デメリット: XIAOのRTCレジスタ容量制限

**案3: 現状維持 + ユーザー教育**
- 「1日1回はアプリを開いて同期してください」と案内
- スマホのバックグラウンド接続サービスで定期的に同期

## 6. 推奨される運用

### 6.1 ユーザー向け

- **1日1回以上、アプリを起動して同期すること**を推奨
- スケジュール時刻通知実装で、通知表示時に自動ポーリング予定

### 6.2 開発向け

- 優先度高: スケジュール時刻ポーリング実装
- 優先度中: バックグラウンド通知受信の改善
- 優先度低: 複数タイムスタンプ保持（必要性が明確になってから）

## 7. 用語集

- **timestamp**: Unixタイムスタンプ（1970年1月1日からの秒数）
- **ポーリング**: スマホから能動的にデータ要求を送ること
- **クリア**: マイコン側のtimestampを0にリセットすること
- **見逃し**: マイコンが通知を送ったが、スマホが受信できなかった状態
